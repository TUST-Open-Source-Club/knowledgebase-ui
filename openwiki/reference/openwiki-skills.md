# OpenWiki Skills Library

The repository tracks two OpenWiki skills under `skills/` (they are not gitignored — `.gitignore` excludes only `.learnings/`, `output/`, `.playwright-cli/`, and build outputs). They are consumed by the scheduled wiki regeneration pipeline ([.github/workflows/openwiki-update.yml](/.github/workflows/openwiki-update.yml) installs `mermaid` and `jsdom` specifically so Mermaid fences can be validated; see [Git Hooks and CI](/openwiki/tooling/hooks-and-ci.md)), and by any agent editing this wiki. Because the wiki is regenerated by that workflow, edits to these skills should be followed by an OpenWiki update run.

## mermaid-diagrams

`skills/mermaid-diagrams/SKILL.md` governs embedding and validating Mermaid diagrams in generated wiki pages.

- **Diagram-type selection**: `sequenceDiagram` for runtime/request flows, `stateDiagram-v2` for lifecycles and state machines, `erDiagram` for data models, `flowchart TD` for branching control flow. Diagrams are grounded in inspected source and each gets a one-line caption below the fence.
- **Syntax-safety rules** (to avoid render breakage): never place semicolons or pipes inside labels; never place unescaped angle brackets in labels (write "returns Promise of User" instead of "returns Promise<User>"); wrap flowchart labels containing parentheses/brackets in double quotes; never use the bare word `end` as a node id and never start a node id with `o-` or `x-` (edge-marker syntax); in sequence diagrams, participant names with spaces need an alias; never use Mermaid reserved words as participant names/aliases/node ids — `note`, `end`, `loop`, `alt`, `opt`, `par`, `and`, `else`, `activate`, `deactivate`, `class`, `state`, `click`, `link`.
- **Update behavior**: a diagram that no longer matches source is a stale claim and must be fixed in the same edit; an accurate diagram must not be regenerated. A diagram that failed to parse is degraded into a plain text fence and marked with an HTML comment `openwiki: mermaid parse failed`; the fix is to repair the syntax from the parser error in the comment, restore the ```mermaid fence, and delete the comment.

## write-connector

`skills/write-connector/SKILL.md` is the procedure for adding a new built-in OpenWiki source connector (relevant only if this repository's OpenWiki instance needs new knowledge-source connectors).

- **Prefer custom MCP**: for arbitrary servers already exposing a read-only MCP server, use the built-in `custom-mcp` connector instead of a new ConnectorId — configure `~/.openwiki/connectors/custom-mcp/config.json` with `enabled`, `transport`, optional `allowedTools`, and optional `readOnlyOperations`; secrets live only in `~/.openwiki/.env` and are referenced as `${ENV_NAME}` in transport headers/env. Add a dedicated built-in connector only for provider-specific auth, scoping UI, or deterministic API pulls MCP cannot express.
- **Required shape**: register the connector in `src/connectors/types.ts` and `src/connectors/registry.ts`; implement it in `src/connectors/sources/<connector>.ts`; expose a `ConnectorRuntime` with `id`, `displayName`, `description`, `backend`, `requiredEnv`, `supportsAgenticDiscovery`, and `ingest()`.
- **State and raw data**: ingestion writes raw JSON/manifests under `~/.openwiki/connectors/<id>/raw/<run-id>/`; state lives in `~/.openwiki/connectors/<id>/state.json`; config in `~/.openwiki/connectors/<id>/config.json`.
- **Security rules**: never read/print/log/return/hardcode secret values; do not store credentials in connector config, raw files, state, logs, or tests; validate connector IDs and raw file paths so reads/writes stay inside `~/.openwiki/connectors/<id>/`; use deterministic ingestion for credentialed fetching; treat wrapped MCP servers as read-only with allowlisted operations.
